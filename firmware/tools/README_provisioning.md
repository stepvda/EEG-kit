# THE PROVISIONING STATION: WHAT SHIPS HERE, AND WHAT IT STILL NEEDS

**Document:** this file, `firmware/tools/README_provisioning.md`

**Governing documents:** FW-EEG-001 Rev C section 7, ASM-EEG-007 Rev B section 6.1,
TST-EEG-004 Rev C T6, PKG-EEG-015 Rev B section 5, JIG-EEG-009 Rev B section 3

Everything generated is regenerable and checkable:

```sh
python3 atecc608b_config.py --check          # the template files match their generator
python3 calibration_schema.py --check        # the schema and the example match the table
python3 provision_selftest.py                # the station's own logic, with no hardware
```

All three exit non-zero if something has drifted, so they can be run as a station check at
shift start.

## 2. Running the station

```sh
python3 provision.py --port /dev/ttyACM0 --serial TIOV-B-0007 \
        --calibration cal_TIOV-B-0007.json \
        --out records/TIOV-B-0007.json \
        --write-config --lock
```

Rehearse first, with no unit connected and no board in front of the operator:

```sh
python3 provision.py --port /dev/ttyACM0 --serial TIOV-B-0007 --dry-run --write-config --lock
```

The dry run prints every step, shows the confirmation box the operator will be asked to read,
and touches nothing.

**The two irreversible steps are both behind a flag.** `--write-config` writes the
configuration-zone template; `--lock` permits the lock, and the lock also needs the unit serial
echoed back -- typed at the prompt, or passed as `--confirm-serial TIOV-B-nnnn` on a station
with no terminal. `--serial` itself is checked against PKG-EEG-015 section 5 before anything is
opened, so a mis-scanned barcode stops the run rather than propagating into the USB descriptor,
the label, the Data Matrix and the record.

**`--lock` without `--write-config` is refused.** Locking a configuration zone this station did
not write locks whatever the part arrived with -- on a factory-fresh ATECC608B, the default
Microchip configuration -- which scraps the breakout without ever creating a device identity.
The escape hatch, for a zone written by some other tool and verified, is
`--lock-unwritten-config`, named after what it does.

**If the template does not reach the part, the run stops before the lock.** The shipped firmware
has no opcode for the configuration-zone write (item 7 below), so today `--write-config --lock`
ends at that stop, with the part and the board intact and the record saying why.

## 3. The step order, and why it is not FW-EEG-001 section 7.3's

That table puts GenKey at step 3 and the configuration-zone lock at step 8. On a factory-fresh
part that cannot work: the part will not generate a key into a slot whose configuration has not
been written and locked, so step 3 fails -- and step 8 would then lock the default
configuration. The script runs the write and the lock as steps 2b and 2c, before GenKey, and
what remains at step 8 is the read-back that confirms the lock took, which is what T6's
acceptance limit asks for. Old step 9 read the provisioning state with that same `0x48`, so the
two are one step, printed as `8/9`, rather than an identical command sent twice with nothing in
between. A new step 7b reads the calibration constants back and compares them, which is the
other half of T6's limit. FW-EEG-001 section 7.3 already says the script governs where the two
differ; the table still needs correcting, and that document is not this station's to edit.
ATECC608B_CONFIG_TEMPLATE.md section 5 gives the corrected table.

## 4. What this station needs from other owners

Each item names what is missing, what it blocks, and whose it is. The numbering is cited from
the source, so it is stable: do not renumber it.

1. **The unit of `k` in the lead-off calibration.** TST-EEG-004 T10 records "8 pairs of (R_off,
   k)" and states neither the unit nor the range of the slope. Until the programme says whether
   the raw lead-off reading is in ADC counts or in ohms, two shops can produce two numbers that
   are both valid against the schema and not comparable with each other -- which is the
   confound RFQ-EEG-001 section 9 exists to prevent. `calibration_schema.py` carries the field
   and says the unit is unstated rather than choosing one. **Owner: the programme, in
   TST-EEG-004 T10.**

2. **The width of the codec volume register.** T17 records "the level register value read back"
   and T28 publishes "the clamp register value", and no document in the package says how wide
   that register is. The schema can therefore require an integer and a lower bound of zero, and
   cannot impose an upper bound -- so a clamp value that is out of range for the part passes
   validation. RFQ E-29 is enforced by that number. **Owner: the programme, once the codec is
   chosen; DSN-EEG-003 or FW-EEG-001.**

3. **A conforming calibration file does not fit in one command frame.** `CMD_WRITE_CALIBRATION`
   (`0x46`) writes its whole payload as one NVS blob in a single frame, and there is no chunked
   form. A CMD payload is at most 255 bytes, because FW-EEG-001 section 5.1 carries the length
   in the one-byte `n_samples` field, and `main.c` `rx_poll()` holds 256 bytes in its receive
   accumulator and silently drops the rest of a longer frame. The shipped example is 1 307 bytes
   minified. **So T6 cannot be completed as specified for any real constant set.** `provision.py`
   computes the frame length before it sends anything and refuses with this diagnosis rather
   than truncating the constants. Two ways out, both the programme's to choose: give `0x46` a
   leading `u16` offset so the blob can be sent in pieces, or define a compact binary encoding
   of the constants. **Owner: the programme and the firmware volunteer; FW-EEG-001 sections 5.1
   and 6.3, `main.c`.**

4. **`n_samples` is filled in three different ways on host-to-device frames.** FW-EEG-001
   section 6.1 says it carries the payload length and defines the payload as the opcode plus its
   arguments; `provision.py` writes the argument length, one less; `webtest/js/protocol.js`
   `buildCommand()` writes 0. `main.c` ignores the field for commands -- `rx_poll()` dispatches
   on the decoded body length -- so nothing misbehaves today, and `provision.py` leaves the byte
   exactly as it was rather than changing a shared header field unilaterally. It is a trap for
   whoever writes the next host. **Owner: the programme; FW-EEG-001 section 6.1 decides, then
   both hosts follow.**

5. **The NVS namespace and partition in every document are not the ones the firmware uses.**
   `main.c` `handle_provision()` writes the keys `unit_serial`, `usb_ids`, `hw_rev` and `calib`
   through `drv_nvs_set_str/blob()`, and `drivers.c` lines 435-457 open namespace **`"tiov"` in
   the default `nvs` partition** for all four. FW-EEG-001 sections 2.5 and 7.3 and ASM-EEG-007
   section 6.1 step 5 specify `eegcfg` in the `prov` partition and `eegcal` in
   `calib`; those two partitions are declared in `partitions.csv`, are never initialised --
   there is no `nvs_flash_init_partition()` call anywhere -- and are never opened. **The code is
   the fact here, and the documents are what need correcting.** Two consequences, and the second
   is the serious one:
   * any readback, service or refurbishment procedure written against `eegcfg`/`eegcal` looks
     in an empty partition and reports an unprovisioned unit. SVC-EEG-013 does not name a
     namespace anywhere -- it requires re-provisioning per F-18 (section 5.8) and leaves the
     storage to FW-EEG-001 -- so the service manual inherits whichever answer is chosen, and
     inherits the wrong one today;
   * identity now shares the 24 kB default `nvs` partition with general settings, and
     `drivers.c` calls `nvs_flash_erase()` unconditionally on `ESP_ERR_NVS_NO_FREE_PAGES`, so a
     full NVS **silently erases the unit serial and the calibration constants of an
     already-provisioned instrument**. That path has to change whichever way the naming is
     resolved.

   **Owner: the coordinator for `drivers.c`, the programme for the four documents.**

6. **The two flash commands in the package are not the same command.** FW-EEG-001 section 9
   writes five images including `0x930000 storage.fat`; ASM-EEG-007 section 6.1 step 4 -- the
   instruction the operator at this station actually follows -- writes four, omits `storage.fat`
   entirely, and names `eeg_fieldkit.bin` where section 9's release list names
   `eeg_field_kit.bin`. An operator following the assembly instruction ships every unit with an
   empty `storage` partition, so the E-16/F-21 reference tone is absent and T17 has no stimulus
   to play; nobody catches it, because the omitted file is not in the command they ran. Nothing
   in the package states what `storage.fat` contains or who produces it. **Owner: the programme;
   ASM-EEG-007 section 6.1 step 4 corrected to FW-EEG-001 section 9's command, and section 9
   stating what the image holds and who builds it.**

7. **Two device opcodes do not exist.** `provision.py` sends them, recognises the refusal and
   says exactly what is missing:
   * `0x4A` `CMD_ATECC_WRITE_CONFIG` -- writes the configuration-zone template.
     ATECC608B_CONFIG_TEMPLATE.md section 4 specifies the payload and the device behaviour.
     Without it, F-18 and E-21 cannot be executed on a factory-fresh part at all.
   * `0x4B` `CMD_READ_CALIBRATION` -- reads the constants back. T6's acceptance limit is
     "constants read back byte-identical to those written", and nothing in the package can read
     them back; `0x48` returns two flag bytes. Without it the step runs, says NOT AVAILABLE and
     records that the limit was not demonstrated on that unit.

   A third may be needed: if Sign requires the ATECC **data** zone to be locked as well as the
   configuration zone, provisioning needs a data-zone lock too, and `drivers.c` exposes only
   `drv_atecc_lock_config()`. That is checklist item 4 of ATECC608B_CONFIG_TEMPLATE.md, and if
   it is required and missing, **T16 cannot pass on any unit**. **Owner: the coordinator;
   `main.c` `handle_provision()` and `drivers.c`.**

8. **`main.c` answers status `0x02` where FW-EEG-001 section 6.2 assigns `0x09`.**
   `CMD_ENTER_PROV` refuses with `0x02` when the configuration zone is already locked -- the
   guard that stops a fielded unit being re-keyed over USB -- and section 6.2 gives `0x02` to
   "bad length" and `0x09` to "locked". An operator reading the status table would go looking
   for a framing fault that is not there. `provision.py` prints the real meaning for both codes.
   **Owner: the coordinator or the programme, whichever end is judged wrong; the code is what
   runs.**

## 5. What is a proposal here, and who must decide it

Two things in this directory are specifications this station wrote because nothing else in the
package had. Neither is a decision this station is entitled to make.

**The ATECC608B configuration-zone template** (`atecc608b_config.*`,
`ATECC608B_CONFIG_TEMPLATE.md`). It is a security decision, it is irreversible once locked, and
one of its four specified bytes carries a bit-field encoding that could not be verified against
a datasheet this station does not have. It has an eight-item reviewer checklist and nobody has
worked through it. **The programme, with a security reviewer, must decide it.**

**The calibration file schema** (`calibration_schema.*`, `cal_TIOV-B-0000.example.json`). Every
key in it is one quantity a numbered test says it records, and every bound in it is a limit that
test states; the key names, the nesting and the identity block are choices. FW-EEG-001 section
10 assigns the calibration-record schema to CAL-EEG-012. **The programme must adopt it, amend it
or replace it** -- the point of writing it down is that it can now be argued with instead of
being invented independently at each shop.

## 6. What is *not* claimed

No unit has been provisioned. No ATECC608B has been written, locked or keyed. The template has
never reached a part. The calibration schema has never been filled in with a measurement,
because nothing has been measured. `provision_selftest.py` proves this station's own logic
against a simulated device and proves nothing whatever about the silicon: TST-EEG-004 T6 on a
real part is still the step that proves the rest.
